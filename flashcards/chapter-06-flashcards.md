## Chapter 6: ETL Design and Multi-GPU Scaling with Dask-cuDF — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What is the default worker topology created by dask_cuda.LocalCUDACluster? | One Dask worker per visible GPU, each pinned to its device via CUDA_VISIBLE_DEVICES. Exam tip: this worker-per-GPU model is the default and standard topology tested. |
| 2 | When is a single GPU (plain cudf, no cluster) the correct exam answer? | When the dataset comfortably fits in one GPU's memory with headroom for intermediate results. Adding a cluster in this case is unnecessary overhead — a classic exam trap. |
| 3 | When should you choose multi-node over single-node multi-GPU (LocalCUDACluster)? | When total working memory demand (base data + shuffle overhead, often ~2x base size) exceeds the aggregate GPU memory available on a single node. Multi-node requires UCX over InfiniBand for fast inter-node communication. |
| 4 | Why do groupby and merge operations in dask_cudf tend to be expensive? | They require a shuffle: rows must be redistributed across workers/GPUs so matching keys co-locate on the same worker. This is communication-bound and shows as GPU idle time with spikes in interconnect (NVLink/network) traffic. |
| 5 | What triggers actual computation in a dask_cudf pipeline? | Calling .compute() (returns a concrete cudf object) or .persist() (materializes into distributed futures kept in memory). Until then, operations just build a lazy task graph. |
| 6 | Command to rebalance uneven dask_cudf partitions before a groupby/merge? | df.repartition(npartitions=N) or df.repartition(partition_size='...'). Exam tip: always repartition after heavy filtering that creates skewed partition sizes. |
| 7 | General rule for sizing dask_cudf partitions relative to GPU memory? | Keep each partition to a fraction of per-GPU memory (not maxed out), leaving headroom for shuffle buffers and intermediate memory spikes during joins/groupbys, which can require multiples of the base partition size. |
| 8 | How does LocalCUDACluster pin each worker to a specific GPU? | By setting the CUDA_VISIBLE_DEVICES environment variable per worker process, so each worker only sees and uses its assigned GPU. |
| 9 | dask_cudf.DataFrame vs cudf.DataFrame — key structural difference? | dask_cudf.DataFrame is a collection of cudf.DataFrame partitions distributed across workers/GPUs with a lazy task graph; cudf.DataFrame is a single in-memory GPU dataframe on one GPU with eager execution. |
| 10 | What causes long GPU idle time with spikes in NVLink/network activity during distributed joins? | The shuffle phase — data must be redistributed across GPUs by join key before local computation can resume. This communication-bound phase is a heavily tested exam gotcha. |
| 11 | Why is UCX important for multi-node Dask-cuDF clusters? | UCX enables high-speed GPU-to-GPU communication (via NVLink intra-node and InfiniBand inter-node) for shuffle-heavy operations, significantly reducing communication overhead versus default TCP. |
| 12 | Common exam trap: dataset fits in aggregate multi-GPU memory on one node — is single-node cluster always sufficient? | No — check peak working memory during shuffles (often ~2x base data size), not just base dataset size vs aggregate memory. If peak demand exceeds node capacity, multi-node is required even though base data alone would fit. |
