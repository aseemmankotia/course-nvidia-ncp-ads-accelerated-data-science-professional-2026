## Chapter 5: cuDF Interoperability, Synthetic Data, and Pipeline Efficiency — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What does cudf.DataFrame.to_pandas() actually do under the hood? | Performs a full device-to-host memory copy of all requested data into a pandas DataFrame. Exam tip: cost scales with data size — avoid calling it repeatedly on large data or inside loops. |
| 2 | What does cudf.from_pandas() actually do under the hood? | Performs a host-to-device copy, allocating GPU memory and transferring the pandas DataFrame's data onto the GPU. Exam tip: only worth it if downstream GPU compute savings outweigh the one-time transfer cost. |
| 3 | How do you convert a cudf Series to a cupy array WITHOUT a host round trip? | Use .values or .to_cupy(). Both use the __cuda_array_interface__ protocol so the cupy array shares the same GPU memory — zero-copy. |
| 4 | cudf method for generating synthetic benchmark data directly on GPU? | cudf.datasets.timeseries(start=..., end=..., freq=..., dtypes={...}, seed=...) — creates a GPU-resident synthetic DataFrame without needing CPU generation or a transfer step. |
| 5 | Why is zero-copy Arrow interoperability useful across RAPIDS libraries (cuDF, cuML, cuGraph)? | They share an Arrow-compatible GPU columnar memory layout, so data passes between libraries without duplication or serialization — unlike to_pandas(), which forces a host copy. |
| 6 | .values on a cudf Series vs. .to_pandas().values — which stays on GPU? | .values (or .to_cupy()) returns a cupy array with zero copy, staying on GPU. .to_pandas().values forces a full device-to-host transfer first. Exam tip: prefer .values for GPU-side numeric operations. |
| 7 | Best practice for column pruning in a cuDF pipeline? | Prune columns at read time (e.g., read_csv(usecols=[...])) rather than selecting/dropping after transforms — this avoids allocating and processing unused columns throughout the pipeline. |
| 8 | Why chain cuDF operations in one expression instead of assigning each step to a named variable? | Chaining lets intermediate DataFrames be garbage collected immediately after use, reducing peak GPU memory. Named intermediates stay alive longer and increase memory pressure, risking OOM on large data. |
| 9 | When is a pandas fallback step acceptable inside a cuDF pipeline? | When cuDF has no equivalent API for the operation AND only a small data slice (e.g., one column, small subset) needs it. Convert just that slice, not the whole DataFrame. |
| 10 | What single factor should drive the decision to justify a to_pandas()/from_pandas() round trip? | Compare the transfer+copy cost (scales with data volume) against the compute time saved by the operation being GPU-accelerated. Small/one-off inspection: fine. Large/repeated in a loop: avoid. |
| 11 | How do you get a 2D cupy array from a full cudf DataFrame for use with cupy.linalg or custom CUDA kernels? | df.to_cupy() (or df.values) — returns a cupy ndarray directly from GPU memory, no host transfer required. |
| 12 | Why generate synthetic benchmark data directly on the GPU instead of generating it in pandas/CPU first? | CPU-generated data requires an extra host-to-device transfer (from_pandas()) before the benchmark even starts, which skews timing results. GPU-native generation (e.g., cudf.datasets, cupy.random-built arrays) avoids this overhead. |
