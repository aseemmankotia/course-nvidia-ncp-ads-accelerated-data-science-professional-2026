## Chapter 10: cuML, GPU-Accelerated XGBoost, and Rapid Hyperparameter Tuning — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | XGBoost GPU tree method: current (XGBoost 2.x) recommended setting vs legacy setting? | Current: tree_method='hist' + device='cuda'. Legacy (deprecated since XGBoost 2.0): tree_method='gpu_hist'. Exam tip: gpu_hist still may appear in older exam questions/docs but 'hist'+device='cuda' is the modern pattern. |
| 2 | cuml.linear_model — key classes | LinearRegression, LogisticRegression, Ridge, Lasso, ElasticNet — same fit/predict API as scikit-learn but GPU-accelerated, accepting cuDF/cuPy input. |
| 3 | cuML RandomForestClassifier vs scikit-learn RandomForestClassifier — main tradeoff? | cuML version trains on GPU with cuDF/cuPy input for major speedup on large datasets; scikit-learn version is CPU-only. cuML wins as row count grows (typically >100K–1M rows); small datasets favor scikit-learn due to transfer overhead. |
| 4 | How to keep cuML output on GPU instead of converting to NumPy? | Set output_type='cudf' or 'cupy' per-estimator, or call cuml.set_global_output_type('cudf') globally — avoids implicit CPU round trip. |
| 5 | How do you build an XGBoost DMatrix directly from a cuDF DataFrame? | xgb.DMatrix(cudf_df, label=cudf_label_series) — or use xgb.QuantileDMatrix() for the GPU hist method, which is more memory-efficient for histogram-based training. |
| 6 | Why prefer QuantileDMatrix over standard DMatrix for GPU hist training? | QuantileDMatrix pre-bins data into histogram quantiles at construction time, reducing GPU memory footprint versus the standard DMatrix — recommended for tree_method='hist' on GPU. |
| 7 | cuml.cluster.KMeans vs cuml.cluster.DBSCAN — when to use each? | KMeans: you know the number of clusters k, centroid-based, scales well. DBSCAN: density-based, discovers cluster count automatically via eps/min_samples, better for irregular cluster shapes/noise. |
| 8 | What is DALI and what problem does it solve? | NVIDIA Data Loading Library — builds GPU-accelerated data loading/augmentation pipelines that feed batches directly into PyTorch/TensorFlow, eliminating CPU-bound dataloader bottlenecks (esp. for image/video/audio pipelines). |
| 9 | How do you hand off cuML/cuPy GPU data to a PyTorch tensor with zero CPU copy? | Use DLPack (to_dlpack()) or the __cuda_array_interface__ protocol — converts cuPy/cuDF GPU memory directly into a PyTorch GPU tensor without a host round trip. |
| 10 | Rule of thumb: when does cuML's GPU acceleration outperform scikit-learn's CPU implementation? | Generally beneficial above roughly 100K–1M rows; below ~10K rows, GPU transfer + kernel launch overhead often makes scikit-learn faster. Exam tests matching algorithm choice to dataset scale. |
| 11 | cuml.linear_model.LogisticRegression — API parity caveat vs scikit-learn? | cuML's LogisticRegression supports a more limited set of solvers (primarily 'qn') compared to scikit-learn's multiple solver options (lbfgs, saga, liblinear, etc.) — API is similar but not 100% feature-parallel. |
| 12 | Best pattern for rapid multi-GPU hyperparameter tuning in a RAPIDS pipeline? | Use Dask-CUDA to distribute trials across multiple GPUs combined with a GPU-aware tuning framework (e.g., Optuna) — avoids CPU-process-based parallelism used by sklearn's GridSearchCV/RandomizedSearchCV n_jobs. |
